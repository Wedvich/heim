# Observability

## Overview

| Layer    | Tool                     | Status  |
| -------- | ------------------------ | ------- |
| Frontend | Sentry (`@sentry/react`) | Active  |
| Backend  | Sentry (planned)         | Not yet |
| Tracing  | Correlation IDs          | Active  |
| Logging  | Structured console       | Active  |

## Frontend — Sentry

Sentry is initialized in `packages/web/src/instrumentation.ts` as a top-level side effect, imported first in `main.tsx` so it captures errors from all subsequent module evaluations.

### Capabilities

- **Error tracking** — uncaught exceptions and unhandled promise rejections
- **Performance monitoring** — page loads, navigations, and core web vitals (LCP, CLS, INP, TTFB) via `reactRouterV7BrowserTracingIntegration`
- **Route-aware tracing** — transaction names match react-router v7 route patterns (e.g., `/settings`) instead of raw URLs. `Routes` is wrapped with `withSentryReactRouterV7Routing` in `App.tsx`.
- **Offline resilience** — `makeBrowserOfflineTransport` queues events in IndexedDB (`sentry-offline`, max 30 envelopes) when the network is unavailable and flushes automatically on reconnect
- **Session context** — `setInstrumentationContext()` tags every event with `tenant_id` and sets the Sentry user to `principal_id` when a session is established. Called from `AuthProvider` on login, refresh, and logout.
- **Trace propagation** — when `CORS_ORIGIN` is set, Sentry attaches `sentry-trace` and `baggage` headers to outbound requests matching that origin

### Sourcemap Upload

The `@sentry/vite-plugin` uploads sourcemaps to Sentry during `vite build`, enabling readable stack traces for production errors. The plugin is a no-op when `SENTRY_AUTH_TOKEN` is absent (local dev).

In CI (GitHub Actions), the build step runs after tests with the required env vars:

- `SENTRY_AUTH_TOKEN` — from GitHub secrets
- `SENTRY_ORG` — from GitHub vars
- `SENTRY_PROJECT` — from GitHub vars

## Correlation IDs

Every API request carries an `x-correlation-id` header — a W3C-compatible 32-character hex trace ID generated by `@heim/logging`. The `apiFetch` wrapper in `packages/web/src/api/fetch.ts` attaches this automatically.

This ID links a frontend action to its backend request chain. The backend can propagate it through event `correlationId` fields for end-to-end traceability.

## Structured Logging

`packages/web/src/logger.ts` provides a lightweight structured logger:

- **Development** — human-readable `[level] message` with optional context object
- **Production** — JSON lines with `level`, `msg`, context fields, and `ts` (epoch ms)
- **Debug** messages are suppressed in production

## Environment Variables

| Variable                 | Required | Description                                |
| ------------------------ | -------- | ------------------------------------------ |
| `SENTRY_WEB_DSN`         | Yes      | Sentry DSN for the web frontend project    |
| `SENTRY_WEB_SAMPLE_RATE` | No       | Traces sample rate (0.0–1.0, default: 1.0) |
| `CORS_ORIGIN`            | No       | Origin for trace propagation headers       |
| `SENTRY_AUTH_TOKEN`      | Build    | Auth token for sourcemap upload (CI only)  |
| `SENTRY_ORG`             | Build    | Sentry organization slug (CI only)         |
| `SENTRY_PROJECT`         | Build    | Sentry project slug (CI only)              |

All `SENTRY_WEB_*` and `CORS_ORIGIN` vars are loaded by Vite via `loadEnv` and injected as build-time constants. `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, and `SENTRY_PROJECT` are read directly by the Vite plugin at build time.
